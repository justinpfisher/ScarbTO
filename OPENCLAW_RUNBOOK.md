## Prepare and review

1. Record the exact candidate commit/tree, requested outcome, source evidence and rendered body/output. Apply the latest enthusiastic, source-grounded Scarb voice to authoritative producers and all their authored surfaces; preserve literal controls, accessibility, official terms, rights and warnings.
2. Verify every factual statement against retained sources. Distinguish inspected/event, added/observed, checked, source-published and public-published dates. Compare the actual rendered output; if a claim cannot be proved, omit it or explain the limited/unavailable source factually.
3. Dispatch a separately configured, isolated reviewer with the exact text, request and sources, not the author's verdict. Preserve run ID, session ID, actual model, reviewed hashes, output and independent verdict. Configured model names alone do not establish actual execution or independence.
4. If delivery stalls, inspect the exact existing run and Gate status before retrying. Recover its result where available; preserve holds and do not create duplicate reviewers or treat silence, a timeout or a fixture as acceptance.
5. A genuine admitted receipt must independently bind the exact body/output, source packet and request. The draft pairs GPT-6 Luna as author with GPT-6.1 Terra as independent reviewer. Under that design, use an accepted catalogue plus an independently built request manifest; accepted-v2 evidence binds packet hash, exact versions/prompts/schema/models, raw slot output, reconstructed writer, final text, independent verdict and measured usage. `compile_catalogue` rejects fixture origins. These are draft requirements, not a claim of live reviewer integration.
6. Apply current repository review and archive rules. Release only approved Scarb-authored text from the migrated producer. Never rewrite historical issued editions or finalised receipts in place: retain original copy, hashes, source evidence, period and first-generation time; use the existing explicit correction/revision mechanism and idempotent generation.

## Use the existing release path

- Dot retains coordination; ask `scarb-release` only for the exact authorised release operation and its evidence. Do not duplicate the release queue, alter protected policy, add credentials/paid services or invent recurring manual editorial work.
- Qualify the exact head with relevant checks; trusted-main tests use `[self-hosted, Windows, X64, scarbto-gmktec]`. Keep untrusted public PR code off the persistent runner. No routine hosted fallback; retain all existing source, access, review and runner holds.
- The workflow serialises `scarbto-pages` without cancelling the running job. Its hosted refresh/Pages job is the existing narrow exception and requires successful GMKtec tests; it is not permission for other hosted processing.
- Root-only runbook/AGENTS edits do not match the publishing workflow's push paths. Do not claim they automatically dispatch, deploy or activate a Gateway.
- For an eligible unchanged-data release, use the existing `code_only` mode and its exact last-good provenance validation, including independently reviewed baseline-pin changes where required. Preserve source timestamps and archives; never describe this as a fresh source collection. Ordinary refreshes retain their existing validation.
- After required review/tests, follow the existing merge → publish → live verification path. Retain reviewed, merged and deployed revisions, Actions results and public HTTP/browser evidence; green CI alone is not live acceptance. Keep last-good publication on anomalies and report the precise unresolved requirement.
